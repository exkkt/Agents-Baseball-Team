# こもれび球団経営室

「見た目はゆるく、経営は本格的」を目指す、ローカルで遊べる球団経営ゲームのMVPです。4球団の架空リーグで、こもれびベアーズのオーナー兼GMになります。

## 起動

Node.js 22以上（開発・検証環境：24）。npm依存パッケージのインストールは不要です。

```sh
cd Agents-Baseball-Team
npm run dev
```

ブラウザで http://127.0.0.1:4173 を開きます。サーバーはこのPCのループバックだけで待ち受けます。本編のゲームデータはブラウザのlocalStorageに保存されます。箱庭には任意のGoogle Drive保存を追加しています（以下参照）。Google Fontsが取得できないときはシステムフォントで表示します。

## 最初の遊び方

1. 「経営プラン」でチケット価格・月次広告費・育成費・商品ごとの仕入れ個数を調整します。試算は本編に影響しません。
2. 「この方針を採用」で、設定・適用月・予測を施策ノートに記録します。仕入れ数は毎月繰り返す設定です。
3. ダッシュボードで「翌月へ進む」。18試合と月次経営をシミュレーションし、自動保存します。
4. 「月次決算」で売上・原価・営業利益・現金・在庫を確認します。「施策ノート」で予測と実績を比較します。
5. 9月末に野球成績が確定します。10月〜3月は更改・補強期間。契約残0年の選手に個別の年俸・契約年数を提示します。3月末の退団で人数が足りなくなる場合は進行を止め、更改・補強を促します。
6. 翌3月に年間決算が確定し、翌4月から次シーズンを継続できます。オフはチケット・飲食売上がなくても固定費が続くため、資金を残しましょう。

セーブアイコンでJSONを書き出し、隣の読み込みアイコンで再開できます。同じ保存状態からは同じ次月結果になります。乱数状態を含めて保存するためです。ブラウザやポートを変更するとlocalStorageは別になるため、移行時はJSONを使います。

上部の葉のアイコンから「はじめから遊ぶ」を選べます。現在の状態を1件バックアップしてから初期化し、同じ画面からバックアップに戻せます。

### セマンティックレイヤー

画面と参謀は、同じ `query()` / `latestMetrics()` / `playerMetrics()` を使用します。登録されていない指標や分析軸は拒否します。SQL・自由式の実行口はありません。

```js
query(state, {
  metric: 'revenue',
  from: '2026-04',
  to: '2027-03',
  groupBy: 'category'
});
query(state, { metric: 'goodsProfit', groupBy: 'product' });
query(state, { metric: 'margin', groupBy: 'month' });
```

- 月IDで重複を除去し、会計明細と試合を多対多結合しません。
- 率は合計分子÷合計分母。月別の率の単純平均は使いません。
- 履歴がない場合や分母ゼロは `null`。画面では「—」です。確認できたゼロとは区別します。
- 現金・在庫残高は最終月の値。期間合計しません。
- 売上は区分別、グッズ粗利益・在庫・回転率は商品別に分析できます。選手別指標はシーズンの打率・防御率・年俸／勝利・年俸／安打です。
- 試合のみ日次記録を持ちます。会計は月次確定のため、日次売上は推定生成しません。
- 指標横の `i` ボタンで定義・分析軸・最新期間・円単位の値を確認できます。選手指標はルールブックにも定義しています。
- 予測は別の需要モデルです。実績指標ではなく、明示した仮定と感度幅を持つ将来シナリオとして表示します。

### 会計と試合

- 内部金額は整数円、通常表示は万円（丸めあり）。グッズ単価とチケットは円。
- 売上は当月入金。グッズは仕入れ時に現金を支払い、販売分だけ売上原価を認識します。一定取得単価で在庫を評価します。
- 選手年俸は契約年額÷12を毎月費用・支出にします。費用計上時の円単位四捨五入により年額と最大数円の差があり得ます。
- `営業利益 − 在庫増減 − 借入利息 = 営業・仕入れ現金増減`。
- 借入は5,000万円単位・累計上限15,000万円、月利0.5%。元本は据え置き。借入時の現金増加は財務履歴に記録し、売上や営業利益には入れません。
- 4〜9月、各球団月18試合・ホーム9試合、通年108試合。各対戦は月6試合。各日1試合以内の簡略日程です。
- 簡略打席から安打・本塁打・打点・得点・アウトを生成。同点は記録付き決着本塁打で処理。投手1人が9回を担当し、勝敗・失点・投球アウトを記録します。
- 四死球・失策・犠打・引き分け・継投・詳細な守備位置適性・プレーオフは省略します。
- 負傷中は起用優先度を下げ、健康な選手を優先します。人数不足時は限定出場します。投手2人・野手9人を必須とします。
- 育成・加齢・疲労は能力や試合に影響。人気は観客需要とグッズ需要、成績・広告・価格はファンの熱量に影響します。
- 現金不足は警告表示と資金調達の対象です。MVPでは即座にゲーム終了にはせず、立て直しの操作を続けられます。

### 参謀とLLM差し替え

現在は画面に明示した**ルールベースのデモ**です。実際のLLMには接続していません。

`advisorProvider.analyze(publicContext, question)` が差し替え境界です。`setAdvisorProvider(provider)` で交換できます。`advisorContext(state)` は公開済みの契約・選手能力・月次履歴と共通指標だけを渡し、本編の乱数状態や未来結果を除外します。返す構造は `RuleBasedAdvisor.analyze()` を参照してください。

実サービスへの接続ではサーバー側アダプターを追加してください。クライアントにAPIキーを置かず、モデルには登録指標IDと算出済みの値のみを渡します。返却された提案を検証し、事実欄の数値は元の指標値と照合する必要があります。現在のMVPはこの外部通信を実装・実行しません。

参謀の出力は、確認済みの数値と期間、データ不足、仮説、推奨と代替案、予測と前提、リスク、検証時期に分かれます。採用されるまで状態は変わりません。単なる前後差を因果効果とは表現しません。

## 球団の箱庭（24時間の生活 × 練習試合 × ローカルLLMの判断 × 分析室）

GM・監督・コーチ・選手・アナリストが、それぞれの予定と判断にしたがって24時間を過ごす見下ろし型のドット絵です。選手は寮で眠り、起きて朝食をとり、練習し、夜は自主練・ケア・自由時間を過ごして眠ります。スタッフは通用口から出勤・退勤します。小野アナリストは練習・睡眠の記録を調べてレポートを作り、関係者に伝えます。経営ゲーム本編とは独立したページで、本編のデータには影響しません。

```sh
npm run dev   # http://127.0.0.1:4173/ballclub.html
```

### 使い方

- **時間**：標準（1×）は「現実の1秒＝ゲーム内の10秒」。24時間は現実で約2時間24分、9:00〜18:30 の練習時間帯は約57分です。2×・4×はこの標準に対する倍率です。人物の歩行・投球・スイング・ボールは 1× で自然な速さです。
- **朝まで早送り**：19:00〜06:30 に押せます。途中の睡眠・回復・作業を通常と同じ刻みで計算しながら 06:30 まで進めます（時計だけを飛ばしません）。LLMの判断が必要になったとき、または警告が出たときは止めて一時停止します。
- **一時停止**：時計・練習・成長・分析作業・判断の要求が止まります（推論中の1件は終わり次第、再開後に反映）。
- **練習試合**：上部の「試合」で日程・スコア・守備と走者・打席経過・両軍の打撃／投手成績を確認できます。週の2・5日目13:00に自動で組まれ、手動でも予約できます。監督が開始30分前に打順と9つの守備位置を決め、球数が増えると継投を検討します。同じLLMキューで同時推論1件・重複防止を維持し、開始や継投の期限を過ぎた場合はルール代替と明示します。
- **試合の計算と記録**：12選手（控え・救援を含む）が生活・育成と同じ能力・調子・疲労で出場。投球条件からの判定と専用の保存可能な乱数を使い、得点・安打・打点・投球数を積算します。9回制、延長12回同点で終了。DH・盗塁・失策・犠打・死球は省略しています。理由は検証済みの起用意図から選び、LLMにスコアを作文させません。試合中は通常練習を止め、出場負荷を疲労に加えます。試合途中も保存・再開できます。
- **試合後の分析**：終了した試合の個人成績が分析室に追加され、小野は既存の受付→収集→集計→考察→報告の作業を経て監督・対象選手へ共有します。分析画面と小野は同じ指標定義（打率＝合計安打÷合計打数、投球回は内部でアウト数）を使います。終了前の試合や過去の未実施試合の成績は補完しません。日次のDrive記録にも試合の打席詳細と個人成績を含めます。v1/v2セーブは時計・元の選手の状態・記録を保ってv3へ移行し、ブラウザ内に移行前のコピーを残します。
- **分析室**：上部の「分析室」、または小野アナリストを選んで「分析室を開く」。期間（直近3/7/14/30日・全期間・日付指定）と選手を選ぶと、チームの概要・選手比較表・推移グラフ（能力・起床時の疲労・睡眠の質）・メニュー別の時間と成果・小野のレポートを見られます。表やグラフには期間・単位・記録件数・集計した時点を表示し、記録が少ない値には「少」を付けます。グラフはカーソルを合わせると値と件数が出て、「表で見る」で同じ値を表で確認できます。
- **分析の依頼**：分析室の「分析を依頼する」で選手（4人まで）・テーマ・期間・質問を送ります。小野が出勤中なら順番に、勤務外なら出勤後に着手します。
- **人物の詳細**：今日の方針、いまの行動と残りの予定（就寝時刻まで）、判断の状態（判断待ち・推論中・行動実行中・睡眠中・勤務時間外）、保留中の報告・相談、直近の予定変更とその理由、今日のLLM呼び出し回数（統計。上限なし）、前回の睡眠（就寝〜起床・途中で目覚めた回数・質・疲労）。

### ローカルLLMへの接続

- ブラウザは Ollama に直接つながず、`server.mjs` の `/api/llm/status`・`/api/llm/decide` を経由します（このPCのループバックのみ）。
- モデルは全員で 1 つを共有し、推論はアダプター側でも画面側でも**同時に 1 件**です。小野アナリストの調査も同じキューを使い、別のモデルは読み込みません。
- 既定のモデルは `gemma4:26b`。変更は環境変数で行います。

```sh
BALLCLUB_MODEL=gemma4:26b OLLAMA_HOST=http://127.0.0.1:11434 BALLCLUB_LLM_TIMEOUT_MS=60000 PORT=4173 node server.mjs
```

- 接続失敗・時間切れ・不正な応答は、その判断だけを**ルールで代替**し、「ルール代替：接続失敗」などと表示します（LLMの判断としては扱いません）。2回続けて失敗したら30秒は問い合わせを控えます。上部の「LLM／ルール」で切り替えられます。旧デモ台本は `ballclub.html?mode=demo`（従来の速さ）。

### 判断と実行の分け方（一日の方針と予定 → 予定の実行 → 区切りでの見直し）

| 層 | 担当 |
| --- | --- |
| LLM（またはルール） | 起床時の「今日の方針と予定」（午前・午後・夜・就寝時刻）、予定が尽きたときの次の予定、疲労での見直し、届いた報告・提案の検討（採用・見送り・保留）、コーチの振り返りと提案、監督の明日の方針、GMの球団方針、出勤時のスタッフの今日の方針、小野の調査計画・追加調査・考察 |
| プログラム | 時間割（起床・食事・身支度・就寝）、移動・練習動作、時間経過、疲労と経験・睡眠と定着の計算、予定の切り替え、即時の制約、集計、記録、保存 |

- **日次の回数上限はありません**（旧版の `BUDGET` は撤廃）。回数で判断を拒否したり、ルールへ切り替えたりしません。呼び出し回数は人物ごとの統計（`calls.today`・`calls.total`）として数え、活動日の区切り（04:00）で今日の回数だけリセットします。
- **LLMを呼ぶのは区切りだけ**：起床時の予定、予定が尽きた（残り20分以上）、疲労が70を超えた、届いた報告・提案があるときの次の区切り（練習の切れ目・食事の前後・出勤時など）、コーチの振り返り（10:30・15:00）、監督の振り返り（17:30）→GMの方針、出勤時の方針、小野の分析。予定済みの次の行動へ移る・食事・移動・休憩・就寝は予定とルールで実行し、LLMは呼びません。眠っている人には判断を要求せず、要求は起きるまで待ちます（深夜は全員が寝ているので推論しません）。
- **報告・提案は保留して区切りでまとめて検討**：受け取った人の「知っていること」に入り、判断が必要なものは保留中の項目になります。緊急でないものは実行中の練習を中断せず、次の区切りでまとめて検討します。疲労が高い人への休養の提案は急ぎとしてすぐ検討します。採用・見送り・保留を記録し、判断済みの項目は繰り返しません。
- **一つの相談の終わり方**：採用・見送りで終了、保留は60分後に再検討、保留が3回目になったら「進展がないため終了」。コーチは、本人が検討中の相手や、状況（疲労・直近の練習）が変わらないまま見送られた相手には同じ提案を送りません。状況が変われば同じ話題でも再検討します。報告→提案の連鎖は2段まで。これは一つの相談を区切るためのもので、同じ日の別の相談は止めません。
- **キュー**（`brain.js`）：同じ人物・同じ出来事の要求は、待機中・推論中・反映待ちを含めて重複させずにまとめます。優先度（疲労＞急ぎの検討＞起床時の予定＞次の予定…）に待ち時間（ゲーム内1分ごとに+2）を足して選びます。待ちが10件以上のときは、緊急でない要求（検討・振り返り・方針・分析）を15分後回しにします（ルールへは切り替えません）。時間帯が終わって不要になった「次の予定」は取り消して記録します。
- **検証と再検証**：応答は許可された ID・範囲だけを受け入れ、調整した点を記録します。判断を出した時点から予定や時間帯が変わっていた応答は実行しません。
- **プログラム側の制約**（LLMの順番を待たずに即時）：疲労60以上で「強め」は「通常」に、75以上で「軽め」に、88で練習を止めて休憩。1日の練習は球団方針の上限（200〜260分）まで。場所が使用中なら代わりのメニュー。

### 24時間の生活と睡眠（ゲーム内の仮定）

- **時間割**：起床（06:00〜07:15、人によって違う）→ 身支度 → 朝食 → 練習の準備 → 午前練習（9:00〜12:00）→ 昼食（疲れていれば仮眠）→ 午後練習（13:00〜17:30）→ 夕食 → 夜（自主練・ケア・自由時間）→ 就寝（予定で 21:30〜23:30）。夕食の時点で疲労70以上なら就寝を 22:00 に早めます。
- **寮**：東側に選手寮（1人1台のベッド）を追加しました。ケアルームの治療ベッドは寝床に使いません。スタッフは勤務時間外は帰宅し（画面から消える）、小野は分析が残っていれば 23:30 まで残業します。
- **睡眠は行動**：寮のベッドに着いて眠り始め、起床で終わります。疲労は眠っている1分ごとに回復し（夜中に目覚めている間は回復しない）、経験の定着と翌日の調子・揺らぎは起床時に一度だけ計算します。定着の量は眠った長さに比例（標準 450 分で満額、昼寝は少し）。定着した分だけ未定着の経験が減るので、日付をまたぐ睡眠・昼寝・中断があっても同じ経験が二重に能力へ変わることはありません。
- **夜の自主練と夜更かし**：自主練は疲労がたまり、就寝前90分以内の練習は睡眠の質を下げ、遅く寝るほど睡眠が短くなります（起床は 07:15 まで）。20日×100シードで「毎晩の自主練＋夜更かし」が通常より伸びないことをテストしています。
- **画面**：時間帯で明るさが変わり、夜は人のいる部屋だけ照明がつきます（寝静まった寮は常夜灯程度）。夜に屋外で練習する人がいればグラウンドの照明がつきます。暗さは人物と操作対象を見失わない程度に抑えています。

### 成長ルール（ゲーム内の仮定）

`growth.js` が計算し、LLM に増加量を決めさせることはありません。現実の人体を再現するものではありません。基礎能力（20〜99）、調子（−1〜+1、成長には使わない）、疲労（0〜100）、練習経験（1分ごとに積算）、逓減・疲労補正・睡眠補正・指導補正・日と回の揺らぎは従来どおりです（`TUNING`・`MENUS`・`INTENSITY`）。睡眠補正には「その日の練習の前に終わった主な睡眠」の質を使います。

### 長期の記録と共通の集計（分析室と小野で同じ）

- **記録**（`records.js`）：人物の短期記憶や画面の出来事ログとは別の、追記だけの記録です。練習1回ごと（選手・活動日・開始・終了・メニュー・強度・実行時間・練習前後の疲労・能力別の獲得経験と見込み・使われた睡眠のID・自主練かどうか・出どころ）、睡眠1回ごと（就寝・起床・実際の睡眠時間・途中の目覚め・質・就寝時と起床時の疲労・定着した経験と能力の増加・寝た活動日と効く活動日）、活動日ごと（能力の開始値・終了値・練習時間）、介入（予定変更・指導・提案と返答・休養・方針・報告への判断）。形式のバージョン付き。
- **睡眠と練習のつながり**：練習記録の `sleepId` が「その練習に効いた前夜の睡眠」、睡眠記録の `forDay` が「その睡眠のあとに始まる活動日」です。当日の夜に始まった睡眠（`startDay`）とは区別します。
- **活動日**は 04:00 で切り替わります。日別の記録を閉じる・練習量と逓減のリセット・判断回数の統計のリセットはこの境界で一度だけ行います。日付が変わっても進行中の練習・分析・保留中の報告は消えません。
- **保存期間**：練習の詳細と介入は30日分、睡眠は180日分、日別は365日分をこのPCに残し、それより古い分は原本をSQLiteまたはDriveに保存できた日だけブラウザから整理します。分析中・原本未保存のデータは削りません。SQLiteの原本は期限で自動削除しません。
- **共通の指標**（`metrics.js`、本編の `semantic.js` と同じ方針の箱庭用）：練習時間・獲得経験・練習1時間あたりの獲得経験・見込みに対する練習成果・能力の成長量・睡眠の質・睡眠時間・起床時の疲労・就寝時の疲労。ID・名称・式・単位・分析軸（選手・メニュー・能力・日・全体練習／自主練）・既存セーブの扱いを定義し、登録外の指標や軸は拒否します。率は合計分子÷合計分母、分母ゼロは「—（分母ゼロ）」、記録なしは「—（記録なし）」で、確認できた0と区別します。経験値と基礎能力の増加は別の指標です。平均疲労は「起床時」「就寝時」の場面に固定しています。
- **既存セーブの記録**：旧版のセーブには日別の履歴（直近30日の練習時間・経験・夜の計算の睡眠の質と疲労・成長）しかないため、それだけを「既存セーブから取得」として取り込みます。メニューの内訳・就寝時刻・見込み値はなかったものとして扱い、作りません（該当する指標では「対象外」と表示）。

### 小野アナリスト（`analyst.js`）

- **きっかけ**：定例分析（2日目以降、毎日 09:30 ごろ・前日までの3日）、週の振り返り（8日目以降の7日ごと）、監督の依頼（一日の振り返りで指名）、オーナーの依頼（分析室）。1件ずつ順番に処理します。
- **段階**：依頼受付 → 記録の収集 → 集計 → 考察 → レポート完成 → 関係者への報告。各段階にゲーム内の作業時間（10・25・20・30・10分）があり、分析室のPCで作業している間だけ進みます。食事・退勤中は進みません。作業時間と実処理（LLM・Drive）の両方が終わってから次の段階へ進み、実処理の進み具合は架空の%ではなく「LLMの順番待ち・推論中」「Driveから取得中」と段階で表示します。
- **データの固定**：着手した時点の記録番号で対象を固定し、作業中に増えた記録はそのレポートに入りません。
- **選べること**（検証済みの構造化ツールだけ。自由なコードやSQLは実行しない）：調べる選手（4人まで）・期間と比較期間（各60日まで）・指標（6個まで）・Driveの過去記録を取るか、追加の集計（1回3件・2回まで、分析軸つき）。Driveは球団専用フォルダの記録だけを、検索2回・取得4ファイルまで。取得したファイルは同じセッション中は再利用します。
- **数値と文章**：数値は共通の集計（metrics.js）が計算し、LLMには計算済みの値だけを渡します。報告文に集計にない数値があれば、その文を除きます。「原因」「〜のせいで」など因果を断定する文も除き、レポートには「観察であり原因は確認していない」と必ず書きます。選手IDや指標IDは名前に直します。
- **レポート**：ID・作成日・対象期間・対象選手・指標・参照した記録と件数（既存セーブ分・Drive分）・確認できた事実・考察・提案・データ不足と不確実な点・報告先と報告状況・判断の出どころ（LLM／ルール代替）・調べた手順。
- **報告と判断**：完成したレポートは分析室に公開し、小野が相手のところへ歩いて行って伝えます（監督には必ず、提案の判断者と担当コーチにも）。受け手の「知っていること」と検討項目に入り、受け手は次の区切りで採用・見送り・保留を決めます。眠っている・帰宅している相手には起きてから・出勤してから伝え、寮の自室にいる相手には次に会えたときに伝えます。採用した提案は実際に反映します（翌日の方針の変更・強めの練習を明日まで控える・残りの予定にケアを入れる・今夜の就寝を早める）。

### 時間・速度・保存・再現

- 動作の時間（`Club.t`、秒）とゲーム内の時計（`Club.gm`、分）を分け、1/60 秒刻みで両方を進めます（`stepper.js`）。1×・2×・4×・早送りは1フレームあたりの刻みの数が変わるだけなので、同じゲーム内時間・同じ判断なら結果は一致します（テストで確認）。通信のタイムアウトは現実の時間です。
- ゲーム内30分ごと・一時停止時・ページを閉じるときに、ブラウザの localStorage（`ballclub-agents-v1`）へ自動保存します。睡眠中・移動中・分析中・判断待ちでも保存でき、開き直すと続きから再開します。
- **旧版のセーブ（v1）**は読み込み時に新しい形式（v2）へ移行します。移行前のデータはこのブラウザの `ballclub-agents-v1-backup-v1` に1件そのまま残します。進行（日数・能力・記憶・予定）は初期化せず、旧版の判断回数は上限のない統計として引き継ぎ、コーチの提案の判断待ちは「届いた提案」に移します。Driveから旧版のセーブを読み込んだ場合も同じく移行します。
- 判断の記録（`director.decisions`）を `new AgentDirector({ seed, replay })` に渡すと、LLM を呼ばずに同じ判断を同じ分に反映し、同じ成長を再現します。

## Google Driveへの保存（箱庭）

箱庭の右側に「Google Drive」欄があります。既存のDriveファイルを上書き・削除しません。

1. Google CloudでDrive APIを有効化し、`drive.file`を許可したデスクトップ アプリ用OAuthクライアントを作成します。個人アカウントのテスト中アプリでは、自分のアドレスをテストユーザーに追加してください。
2. ダウンロードした設定JSONをダウンロードフォルダに置きます。`client_secret*.json`、`credentials*.json`、`diamond-gm-oauth.json`の候補が一つなら自動検出します。複数ある場合や、macOSのアクセス許可の都合でダウンロードフォルダを読めない場合は、起動時の`BALLCLUB_GOOGLE_CREDENTIALS`に使用するファイルの絶対パスを指定します（ファイルの中身を出力しないでください）。ダウンロードフォルダの一覧が5秒以内に返らないときは、待ち続けずにその旨を表示します。`.env`ファイルを読む処理はありません。
3. サーバーを起動し、箱庭の「Googleに接続」を押します。別タブで本人がログインして許可し、完了後に箱庭の「接続を確認」を押してください。`?paused=1`で開くと、人物を動かさず接続の準備ができます。
4. **セーブ**：「Driveへ保存」を押した時だけ、マイドライブの専用フォルダ`AI Agents Baseball Team`に新規セーブを作ります。「保存一覧」はセーブ（種類 `save`）だけを表示し、「読み込む」で復元できます（旧版のセーブは移行してから読み込み）。直前の状態をPC内に1件退避し、「読み込み前に戻す」で入れ替えられます。
5. **記録とレポート**：専用フォルダの中に `記録（練習・睡眠・日別）`・`分析レポート` のサブフォルダを作り、活動日ごとの記録ファイルとレポートを1件ずつ保存します。ファイルの付帯情報（種類・日・対象選手・進行の系統）が検索用の小さな索引になり、小野は中身を全件ダウンロードせずに必要な日だけ取得します。
   - **初期状態は手動**：「記録を送る（未送信 N件）」を押した時だけ送ります。「日ごとの記録とレポートを自動でDriveへ送る」にチェックを入れると、自動保存のたびと20秒ごとに未送信分を送ります。
   - 送信に失敗した分は未送信として残し、手動または時間をおいて（30秒から最大10分まで間隔を延ばして）再送します。同じIDのファイルがDriveにあれば新しく作らないので、応答が途中で切れた後に再送しても重複しません。Driveでの保存を確認できたものだけ「保存済み」と表示します。

設定JSONはブラウザやLLMへ渡しません。サーバーが必要時に読み込み、認証コード・トークン・Googleの生のエラーはログや応答に出しません。OAuthはstate検証・PKCE・ローカルのコールバックを使用します。認証トークンは`.local/drive-token.json`に保存し、フォルダは700・ファイルは600の権限にします。`.local`はGit対象外で、静的公開する`dist`の外にあります。

「接続設定済み」はPCに認証が保存されていることを示し、Googleへの実際の接続は保存・一覧取得時に確認します。期限切れや権限の取消しは再認証してください。テスト中の外部アプリでは、通常7日でリフレッシュトークンが失効します（[Google公式](https://developers.google.com/identity/protocols/oauth2#expiration)）。

検証は模擬Google応答（メモリ上の模擬Drive）で、認証・トークン更新・保存／復元・専用ファイルへの制限・認証情報の非公開・記録の送信失敗と再送・重複防止・保存一覧との分離・索引での絞り込み・取得の再利用を確認しています。実際のDriveへの記録・レポートの送信は未確認です（下記）。

### 1球記録と長期保存（投球モデル pitch-v1）

新しい試合は1球ずつ球種・狙い・制球によるばらつき・球速を決め、その条件から見送り／空振り／ファウル／打球を判定します。カウント、回・表裏、点差、アウト・走者、打者・投手の左右、球種、球速(km/h)、位置、判定と終球の結果を記録します。xは捕手から見た左右（-1〜1がストライクゾーンの端）、zはゾーン下端0・上端1です。内外角は打者の左右に依存するため座標を原本にします。生成モデルの記録であり、実測データに合わせた物理モデルではありません。

「試合」の投球データで打者・投手・投球前カウント・球種・コースを絞り込み、9分割の分布、球速と終球の成績、1球ずつの一覧を確認できます。平均球速は投球数で加重し、全球種とストレートを分けます。CSVは選択試合のDB保存済み全投球です。進行中は直近の保存応答までの記録になります。旧打席モデルの試合は結果を保持し、球速・コース・カウントを後付けしません。

原本は `.local/baseball.sqlite` に保存します（Node.jsの組み込みSQLite、WAL・トランザクション使用）。10球ごと、通常の自動保存、停止時、試合終了時に保存し、閉じた日の練習・睡眠・試合・イベントも日次で保管します。確定済みの試合、保存済みの投球から分岐した記録は黙って上書きしません。元の進行に戻す場合は同じ試合IDの衝突に注意してください。DBの原本と日次保存を確認した後だけ、当日分と直近3試合を残してブラウザ側の古い詳細を整理します。保存エラー時には未保存分をブラウザに保持します。ブラウザ容量不足時は一時停止します。DBの自動削除はありません。

既存のDrive送信設定を維持します。日次バックアップを送る場合、ブラウザで整理済みの原本はSQLiteから取り出して送信します。ローカルDBはこのPCのディスク容量を使用します。DB原本自体の外部バックアップがない間は、PCの故障からは復旧できません。

分析室と小野の共通指標には全球種／ストレートの平均球速、条件別球速、条件別打率、打者・投手の空振り率を登録しています。追加調査では投球前カウント・球種・コース・イニングで分類できます。小野の1回の調査の件数・期間上限は維持し、取り切れない過去期間はレポートに不足として残します。集計後は作業用の原本コピーを解放し、原本を人物の短期記憶やLLMの常時コンテキストに保持しません。
